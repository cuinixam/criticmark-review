# [CMR-002] Escape CriticMarkup markers in sidecar quotes

## Issue

#3

## Summary

As a reviewer, I want to comment on any code in a sidecar review, even code that contains CriticMarkup markers, so that a selection is never refused because of what it contains.

## Description

A sidecar quote holds source text, and source text can contain the closing marker of its own element. Selecting code with `==}` is refused today with "Selection contains ==}, which would break the mark". An agent-written quote holding `--}`, `~~}` or `~>` is cut in the wrong place, and Accept then refuses it or leaves stray text.

CriticMarkup has no escape syntax. Sidecars are read only by this extension and the agent, so they can have their own rule. Inside a sidecar quote, the last character of a marker is written as a numeric character reference, and the parser turns it back when reading:

```text
{line="12"==if (a ==&#125; b)==}{author="Max" date="2026-11-08">>Broken?<<}
```

`==}`, `--}` and `~~}` use `&#125;` for the brace. `~>` uses `&#62;` for the arrow head.

## Scope decisions

- Sidecars only. Markdown reviews stay as they are, so they keep working in the Obsidian Track Changes plugin.
- A quote containing the literal text `&#125;` or `&#62;` is read as the character, so it is not found and its card shows as orphaned. This is rare and loses nothing, so there is no escape for the escape.
- An agent that does not escape gets today's behaviour. The Accept refusal for an unescaped `~>` stays.
- Comment text still cannot contain `<<}`.

## Acceptance criteria

- [ ] Add Comment works on a selection containing `==}`, and the card finds the code again
- [ ] A quote holding an escaped `--}`, `~~}` or `~>` parses as one element and Accept writes the real text
- [ ] The new text of a replacement is unescaped when it is written to the source
- [ ] Markdown parsing does not change
- [ ] `docs/format.md` describes the rule
- [ ] All existing tests continue to pass
