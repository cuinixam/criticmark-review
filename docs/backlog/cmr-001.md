# [CMR-001] ✅ DONE - Review files that are not markdown with a sidecar file

**Status**: Done (2026-11-08)
**Priority**: High
**Component**: `src/markup/`, `src/ui/Decorations.ts`, `src/extension.ts`, `package.json`, `docs/format.md`, `README.md`
**Issue**: #1

**Summary**:
As a reviewer, I want to comment on `.c`, `.py` and other text files from the review panel, the same way I review markdown, so that I can review an agent's code without breaking the syntax of the file.

**Description**:
Inline CriticMarkup breaks the syntax of code files, so the extension only handles markdown today. With this item the threads of a file that is not markdown live in a sidecar file next to it. The review window works with the sidecar in the background: the reviewer never opens it, and the agent reads and replies in it. `foo.c` only changes when the reviewer presses Accept.

File format. `foo.c.review` holds entries separated by blank lines:

```text
{line="42"==static int x;==}{author="Max" date="2026-11-08">>Why static?<<}{author="Claude" date="2026-11-08">>Only used in this file.<<}

{line="57"==if (x > 3) {
    reset();
}==}{author="Max" date="2026-11-08" status="resolved">>Is 3 the right limit?<<}

{line="80"~~return 0;~>return ERR_TIMEOUT;~~}{author="Claude" date="2026-11-08">>The caller expects an error here.<<}

{line="95"--debug_dump();--}

{author="Max" date="2026-11-08">>General comment about the whole file.<<}
```

- Elements, attributes, threads, replies and `status="resolved"` are the ones in `docs/format.md`. There is no new syntax.
- The quoted text in a highlight, a deletion or the old part of a replacement is the anchor. It is the exact source text and may span lines.
- `line="N"` is required on every anchor and is the first line of the quote. It is a hint, used when the same text appears more than once. The extension does not rewrite it when the code moves.
- `before` and `after` are optional hashes of the nearest non-blank line on each side of the quote, written by the extension. They tell repeated text apart after the code moved.
- A comment with `line` and no anchor sits on that blank line. A comment with neither applies to the whole file.
- A bare `{++text++}` is not allowed, because it has nothing in the source to attach to. To add code, write a replacement of the neighbouring line.
- `{=+text+=}` is not used in sidecars.
- New entries are appended. The panel orders cards by position in the source.

Finding the anchor:

- The extension searches the current text of the open editor for the exact quote, on every change to the source or the sidecar. Line endings are treated as equal.
- With several matches it prefers those with matching neighbours, then takes the one nearest to `line`. With no match the thread is orphaned: its card stays in the panel, marked as orphaned, with no highlight. It is never dropped silently.
- A reformat that changes whitespace inside the quote orphans the thread. There is no fuzzy matching.

Behaviour:

- Add Comment is the same command, shortcut and panel card as today. A selection quotes the selected text. A cursor with no selection quotes the current line without its indentation. A cursor on a blank line makes a comment that stays on that line. On submit the source is saved first, so the agent finds the quote on disk. The first comment creates the sidecar.
- The refusals for overlap, code and multiple blocks do not apply to sidecars.
- A cursor inside an anchor opens its card. A selection that differs from every anchor starts a new thread, even when it overlaps one. When the cursor is inside several anchors, the smallest one wins.
- Reply, Edit, Delete and Resolve write to the sidecar and do not touch the source.
- Accept changes the source at the anchor, saves it and removes the entry. It is refused when the anchor is orphaned, and when the quote has several matches and its neighbours do not identify the copy (without neighbours: none starts exactly on `line`). Reject only removes the entry.
- Deleting the last entry removes the sidecar file.
- The extension watches sidecars on disk, so agent replies appear without a reload. The watcher covers workspace folders; a file outside one is refreshed when its editor becomes active.

Differences from markdown:

- The new text of a replacement is not in the file until Accept. The old code gets the red strikethrough and the editor draws the first line of the new code after it. The full text is on the card.
- An orphaned thread has only a card.
- With a stale `line` and repeated code, a highlight can land on the wrong copy.
- A save can run format-on-save, and a whitespace change inside a quote orphans the thread. The extension does not skip the formatter.
- Ctrl+Z does not reach the sidecar, which works like a GitHub pull request review. Comments can be edited or deleted and threads unresolved, but a Delete is final. After an Accept, Ctrl+Z in the source restores the code and the suggestion stays gone.

**Scope Decisions**:
- Sidecar file, not comments in the language's own comment syntax, which cannot carry suggestions or anchor inside a line, and which would compile and ship unnoticed if forgotten.
- `.md` reviews stay inline so the Obsidian Track Changes plugin can show them. There is no sidecar fallback for `.md`, so the current limits in markdown stay.
- The file name has no `.md` ending. Obsidian could not show the source around the threads, and markdown tools would pick the file up.
- The format stays our CriticMarkup. W3C Web Annotation has the same quoted anchor idea but no resolved state or suggested replacement, and SARIF, git-appraise and CodeReview.json do not fit a file that an agent edits in place.
- The setting `criticmarkReview.sidecarExtensions` is an array with default `["*"]`. `[]` means markdown only, and `[".c", ".py"]` means those extensions only. Markdown is always reviewed inline.
- The sidecar is not gitignored and the docs do not suggest it, because an ignored file could hide open review comments. Blocking pushes that contain `.review` files is not a feature of the extension.
- Out of scope: binary files such as PDF or images, sidecar support in the Obsidian plugin, Zed.

**Technical Notes**:
- Sidecars need their own parse mode: code detection off, and a left-to-right scan. With the current patterns a `{--i;` inside a quote could run to the `--}` of a later entry and lose it.
- `parse(text)` with one argument must not change, because it mirrors the Obsidian plugin.
