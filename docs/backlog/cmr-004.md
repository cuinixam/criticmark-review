# [CMR-004] Review a staged file from its diff view

**Status**: Open
**Priority**: Medium
**Component**: `src/extension.ts`, `README.md`
**Issue**: #5
**Autonomy**: review-pr
**Depends on**: CMR-003

**Summary**:
As a reviewer, I want to see and add comment threads while I look at the diff of a staged file, so that I can review from the git view without opening each file first.

**Description**:
When I click a staged file in the git view, the diff opens and both sides are read-only documents with the `git:` scheme: the right side is the version in the index, the left side is `HEAD`. A sidecar review only accepts `file:` documents, so the panel is empty. For an unstaged file the right side is the file itself, so this case already works unless the focus is on the left side.

Markdown has the opposite problem. `reviewable` does not check the scheme, so the panel uses the read-only `git:` document as the file it writes to.

With this item the review always belongs to the file in the working tree. When the active editor shows a `git:` document, the extension loads the matching `file:` document, the same way CMR-003 does for a `.review` file, and the panel shows its cards.

A diff side with exactly the same text as the working file acts as an editor of that file, because the offsets of the cards are valid in it. It gets the highlights, the mark, the cursor sync and Add Comment, and a click on a card selects the anchor inside the diff.

**Scope Decisions**:
- If the text differs, for example in a partly staged file, the panel still lists the cards. A click on a card opens the working file, and Add Comment shows a message and writes nothing.
- A `git:` document is mapped to its working file by changing the scheme to `file` and dropping the query. This relies on how the git extension builds these URIs, because its public API only offers `toGitUri` in the other direction. Matching `repository.state.indexChanges` from the public API is the alternative, at the cost of more code and a dependency on the git extension.
- A `git:` document is never written to. This also applies to markdown.
- An inline markdown comment writes markup to the working file, so the index no longer has the same text. After the first comment on a staged markdown file the diff falls back to the behaviour above for different text. Sidecar reviews do not change the source, so they stay in the diff. An Accept does change it, so the same fallback applies.
- If the file no longer exists in the working tree, for example a staged delete, the panel stays empty.
- VS Code closes a document that has no editor after about three minutes. If the working file closes while the panel still shows it, the extension loads it again.
- Out of scope: comments on removed lines, because that text is not in the working file and the sidecar cannot place it. Comments tied to a commit or a ref.

**Acceptance Criteria**:
- [ ] Clicking a staged `.c` file in the git view shows its cards in the panel
- [ ] With the right side focused and the same text as the working file, highlights are shown and a click on a card selects the anchor inside the diff
- [ ] Add Comment on the right side writes to `foo.c.review` with the quote and line of the working file
- [ ] With the focus on the left side, the panel keeps showing the cards of the file
- [ ] In a partly staged file, a click on a card opens the working file and Add Comment shows a message and writes nothing
- [ ] Reply, Edit, Delete and Resolve on a staged markdown file write to the working file, and nothing tries to write to the `git:` document
- [ ] For a staged delete, the panel is empty and no error is shown
- [ ] The panel still shows the cards after the working file was closed by VS Code
- [ ] `README.md` describes reviewing from the diff view
- [ ] All existing tests continue to pass
